# v4.1 Update Eligibility Gate

v4.1 adds the missing upstream question:

> **Does this installed MOD actually need an update?**

Only after the answer is proven does the item enter Main/Variant/Component planning.

## Pipeline order

```text
MO2 installed metadata + exact local file identity
        ↓
Update Eligibility Gate
        ↓
UPDATE_CONFIRMED only
        ↓
Main / Variant selection
        ↓
Component Discovery + Closure
        ↓
Download / MO2
        ↓
VERIFIED
```

## Evidence hierarchy

From strongest to weakest:

1. Nexus `file_updates` exact chain (`old_file_id -> new_file_id`)
2. a genuinely later compatible Nexus file upload
3. MO2 yellow-arrow-equivalent metadata signal
4. author-entered version / newestVersion strings
5. MO2 red exclamation / Nexus metadata warning UI

The last category is not trusted for update decisions.

## MO2 yellow arrow

MO2's local update state is reconstructed from `meta.ini` fields:

```text
version
newestVersion
ignoredVersion
nexusFileStatus
```

A yellow-arrow-equivalent signal is useful because those mods should be checked first. It is not sufficient permission to update.

If MO2 signals an update but the Nexus Files API cannot prove either an exact successor or a genuinely newer compatible upload:

```text
SKIP_METADATA_FALSE_POSITIVE
```

The item never reaches Main/Component download planning.

## Exact Nexus update chain

If Nexus says:

```text
old_file_id = installed exact fileId
new_file_id = successor fileId
```

and the successor is active and has no hard runtime/body/role conflict, this is the strongest update proof.

An author version typo does not invalidate an exact update chain. Exact file identity is stronger than the displayed version string.

If the chain crosses a hard incompatible variant:

```text
HOLD_UPDATE_ELIGIBILITY
NEXUS_UPDATE_CHAIN_VARIANT_CONFLICT
```

No automatic download occurs.

## Fallback: later compatible upload

When Nexus has no explicit update chain, a later upload may still prove an update if:

- the file is active;
- identity/family compatibility is strong enough;
- no hard runtime/body/role conflict exists;
- `uploaded_time` is truly later than the installed file;
- its version metadata is also monotonically newer.

If the later compatible upload has the same/lower/unreliable version metadata:

```text
HOLD_UPDATE_ELIGIBILITY
```

because the page changed but automatic replacement is not yet safe.

## MO2 false negatives

MO2 metadata may also fail to show a yellow arrow. If Nexus exact evidence proves a newer successor, the project still returns:

```text
UPDATE_CONFIRMED
```

So yellow-arrow parity is a priority signal, not a filter that can hide Nexus-proven updates.

## Ignore Update

`ignoredVersion == newestVersion` is respected. The exact ignored target becomes:

```text
SKIP_IGNORED_UPDATE
```

A genuinely later version can surface again.

## Status model

```text
UPDATE_CONFIRMED
HOLD_UPDATE_ELIGIBILITY
SKIP_METADATA_FALSE_POSITIVE
SKIP_UP_TO_DATE
SKIP_IGNORED_UPDATE
```

Use:

```powershell
npm run updates:status
```

The report separates confirmed updates, eligibility holds, ignored targets, false-positive MO2 metadata signals, and already-current mods.

## Safety boundary

`HOLD_UPDATE_ELIGIBILITY` is upstream of Component Closure.

It may be displayed in Review Center for investigation, but `review-download.js` explicitly refuses to turn such a HOLD into a direct Main download. Otherwise a human click could bypass Patch/Resource/Translation closure.

Eligibility must first become confirmed; only then does the item enter the normal downstream safety chain.

## UI warning policy

MO2 red exclamation icons and Nexus author metadata anomalies are not update facts. They cannot by themselves trigger:

- update;
- redownload;
- Main migration;
- corruption diagnosis;
- force-resubmit.

Exact local file identity + Nexus evidence remains authoritative.
