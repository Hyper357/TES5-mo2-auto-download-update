# v4.1 Update Eligibility Gate

## Purpose

The pipeline must answer two separate questions in order:

1. **Does this installed MO2 mod actually need an update?**
2. If yes, **which exact Main branch and required components should be downloaded?**

Before v4.1 most safety work focused on question 2. v4.1 adds an upstream eligibility gate so false metadata warnings do not enter Main/Component selection at all.

## Evidence hierarchy

### Weak hint: MO2 update metadata

`meta.ini` fields such as:

- `version`
- `newestVersion`
- `ignoredVersion`
- `nexusFileStatus`
- `lastNexusQuery`
- `lastNexusUpdate`
- `nexusLastModified`

are read as useful MO2 update hints. A `newestVersion > version` state approximates the user's visible yellow update-arrow condition.

It is **not download authorization**. Author-entered Nexus version metadata can be stale or wrong.

### Authoritative eligibility evidence

The project resolves the installed Nexus artifact using:

1. exact `installationFile` when it matches a Nexus Files API record;
2. exact installed `fileId` from MO2 metadata;
3. otherwise HOLD when local identity cannot be proven.

The exact installed Nexus file is then compared only with active files in the same semantic lane:

- same file role;
- same stable Main `branchKey` when available;
- for generic Main branches, strong lexical continuity is required rather than treating every Main File as interchangeable.

A newer same-lane file is established from per-file Nexus evidence, primarily `uploaded_time`, with per-file version as supporting evidence.

## States

```text
CURRENT_CONFIRMED
UPDATE_CONFIRMED
UPDATE_IGNORED
UPDATE_UNCERTAIN
MO2_HINT_FALSE_POSITIVE
```

### CURRENT_CONFIRMED

The exact installed semantic lane has no newer active file. It is skipped before Main/Component discovery.

### UPDATE_CONFIRMED

A newer exact Nexus file exists in the same semantic lane. Only this state is eligible to continue automatically into Main/Variant/Component selection.

### UPDATE_IGNORED

A real same-lane update exists, but MO2 metadata indicates the current newest version was explicitly ignored. The project reports it and does not automatically update it.

### UPDATE_UNCERTAIN

The project cannot prove which files belong to the installed update lane, for example a generic multi-Main page with insufficient name continuity. It becomes `HOLD_UPDATE_ELIGIBILITY`.

### MO2_HINT_FALSE_POSITIVE

MO2 metadata suggests an update, but the Nexus Files API does not contain a newer exact file in the installed semantic lane. The action is `SKIP_MO2_FALSE_POSITIVE`; it must not enter the download pipeline.

## Selector disagreement

If eligibility proves a real update but the downstream Main selector later returns `SKIP_CURRENT` or `SKIP_DOWNGRADE`, v4.1 does not silently erase the upstream evidence. It produces:

```text
HOLD_UPDATE_TARGET_MISMATCH
```

This exposes a disagreement between two safety layers for human review.

## MO2 yellow arrow and red exclamation

The yellow update arrow is a useful prioritization hint because it reflects MO2's local update metadata. v4.1 records the equivalent metadata condition as `mo2ArrowHint` and compares it with exact-file evidence.

The red exclamation / metadata warning remains outside the eligibility chain. It cannot by itself trigger update, redownload, Main migration, corruption diagnosis, or force-resubmit.

## Quick status

After an Audit:

```powershell
npm run update:status
```

The compact report separates:

- confirmed real updates;
- MO2 metadata false positives;
- ignored updates;
- uncertain eligibility items;
- confirmed-current mods (optional with `-- --include-current`).

The most useful calibration after first deployment is to compare:

1. MO2 yellow-arrow mods that become `MO2_HINT_FALSE_POSITIVE`;
2. `UPDATE_CONFIRMED` mods for which MO2 showed no arrow.

Those disagreement cases are evidence for improving lane matching without weakening the gate.

## Mandatory pipeline order

```text
MO2 installed identity
        ↓
Update Eligibility Gate
        ↓ only UPDATE_CONFIRMED
Main / Variant selection
        ↓
Variant Decision Memory
        ↓
Component Discovery / Closure
        ↓
Review Center when needed
        ↓
exact modId:fileId execution
        ↓
VERIFIED
```

## Non-goals

v4.1 does not:

- use red warning icons as update evidence;
- blindly reproduce a MO2 UI icon;
- auto-update every file uploaded after the installed file;
- switch between mutually exclusive Main branches to satisfy eligibility;
- install mods or operate FOMOD.

FOMOD-aware analysis remains a later roadmap item after eligibility is calibrated on the user's real MO2 library.
