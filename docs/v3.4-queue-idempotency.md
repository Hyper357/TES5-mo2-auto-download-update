# v3.4 Queue-aware Idempotency

v3.4 addresses a different failure class from wrong file selection: **the correct Nexus file is selected, but the same `modId:fileId` is submitted to MO2 more than once**.

Typical symptoms are MO2 dialogs such as:

- “此文件已在下载队列中” / already in download queue;
- “重新下载?” / re-download?;
- multiple dialogs for the same exact file while Pi Agent is still running;
- a second pipeline run re-submitting an item that the previous run already handed to MO2 but had not yet VERIFIED.

## Root causes

A single run has an `execution-state.json`, but each pipeline invocation creates a new run directory. Before v3.4, a later invocation therefore could not reliably know that an earlier run had already submitted the same exact Nexus file.

MO2 also creates download evidence asynchronously. Between NXM handoff and final archive verification there may be a period where the final archive is not complete yet, while `.meta`, `.unfinished.meta`, or `.unfinished` already indicates that the exact file is in progress.

Finally, two accidental concurrent `--go` processes can race each other and both submit the same NXM.

## New invariants

### 1. Exact Downloads-state guard

Before every NXM submission, `execute-plan.js` calls `scripts/lib/download-guard.js` and scans MO2 Downloads for exact metadata matching both:

```text
modID == target modId
fileID == target fileId
```

The guard recognizes:

- `COMPLETE`: exact `.meta` + non-empty archive + no unfinished sidecar;
- `INFLIGHT`: exact `.meta` but archive not complete;
- `INFLIGHT`: exact `.unfinished.meta`;
- `INFLIGHT`: exact metadata plus `.unfinished` sidecar;
- `ABSENT`: no exact metadata evidence.

`COMPLETE` and `INFLIGHT` both suppress another NXM handoff. The executor goes directly to verification/waiting.

### 2. Cross-run submission ledger

A persistent local ledger is stored at:

```text
.runtime/state/submission-ledger.json
```

It is shared by all pipeline runs and records exact keys such as:

```text
97155:799389
176454:799451
```

Possible states include:

```text
SUBMITTING
SUBMITTED
WAITING_EXISTING
POSSIBLY_SUBMITTED
VERIFY_TIMEOUT
VERIFY_FAILED
VERIFIED
```

A recent active ledger entry suppresses re-submission even if MO2 has not created filesystem evidence yet. Default active TTL is 720 minutes (12 hours).

This intentionally prefers waiting over showing MO2 duplicate/re-download dialogs.

### 3. Single executor lock

Real download execution obtains:

```text
.runtime/state/download-executor.lock
```

Only one `--go` executor may own this lock. If Pi Agent accidentally starts a second real-download process while the first is alive, the second fails with:

```text
CONCURRENT_EXECUTOR
```

The project never resolves this by killing the first process automatically.

### 4. Retry boundary is side-effect aware

Not every `retry=true` error is safe to repeat at the NXM handoff boundary.

Automatic exact re-submit is restricted to failures that are clearly before MO2 submission, for example:

```text
NEXUS_API_429
NEXUS_API_TIMEOUT
CDP_UNAVAILABLE
NXM_EXTRACT_FAILED
NXM_EXPIRED
```

If an error occurs near/after the handler boundary and it is uncertain whether MO2 received the NXM, v3.4 does **not** keep firing the same URL. It records `POSSIBLY_SUBMITTED` and waits for exact download evidence/verification.

Before any retry it also re-scans Downloads. If exact `modId:fileId` evidence appeared after the failed command, the retry is cancelled.

## Status inspection

Show current global ledger/lock summary:

```powershell
npm run queue:status
```

Inspect one exact target:

```powershell
node scripts/queue-status.js --mod-id 97155 --file-id 799389
```

The output contains:

```text
executorLock
ledgerSummary
activeLedgerItems
```

For one target it additionally contains:

```text
disk.status
ledger
resubmitGuard.suppress
resubmitGuard.reason
```

## Recovery rules for Pi Agent

When an item is stuck or verification times out:

1. Do **not** immediately re-run the whole batch.
2. Read `.runtime/state/submission-ledger.json`.
3. Run `npm run queue:status` or inspect the exact target.
4. Check the most recent run's `execution-state.json` and `logs/errors.jsonl`.
5. If the target is `INFLIGHT`, keep waiting/inspect MO2; do not submit again.
6. If the ledger says `SUBMITTED`, `POSSIBLY_SUBMITTED`, `WAITING_EXISTING`, or recent `VERIFY_TIMEOUT`, do not submit again just because a new run started.
7. If the ledger says `VERIFIED` but the archive evidence is gone, the executor raises `LEDGER_VERIFIED_MISSING` instead of silently downloading another copy.
8. `--force-resubmit` exists only as a manual recovery escape hatch. Pi Agent must not use it without explicit user approval and evidence that the old queue/download entry is no longer active.

## Why this reduces MO2 popups

The previous effective sequence could be:

```text
Run A -> submit file 799389 -> MO2 queues it -> verify still pending
Run B -> new execution-state -> submit file 799389 again
MO2 -> “already in queue” / “re-download?”
```

v3.4 changes this to:

```text
Run A -> submit file 799389 -> ledger=SUBMITTED
Run B -> ledger guard sees 799389 -> NO NXM HANDOFF -> wait/verify existing item
```

And concurrent runs become:

```text
Run A -> owns download-executor.lock
Run B -> CONCURRENT_EXECUTOR -> stops before any NXM handoff
```

The identity used for every guard is the exact Nexus `modId:fileId`, not only a filename substring.
