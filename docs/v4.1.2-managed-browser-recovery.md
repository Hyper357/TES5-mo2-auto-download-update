# v4.1.2 — Managed Browser Recovery

## Incident

A real full-library run found confirmed updates but never reached download execution.

Observed facts:

- `browser:start` failed with `CDP_UNAVAILABLE`;
- port 9222 responded to `/json/version` with HTTP 404 / invalid JSON, so the port was occupied by a non-CDP service;
- moving manually to 9229 avoided the collision, but the old manager still preferred the machine's normal Chrome and CDP never became ready;
- Component Discovery therefore marked Requirements/Description coverage as `BROWSER_UNAVAILABLE`;
- Closure correctly changed otherwise-downloadable Main targets to `HOLD_COMPONENT_DISCOVERY`;
- result: zero automatic downloads, despite confirmed updates.

## Root causes fixed

### 1. Non-CDP HTTP service was misclassified as STOPPED

An HTTP responder returning 404/invalid JSON now means:

```text
MISMATCH
portOccupied = true
```

not `STOPPED`.

The manager therefore does not wait for or launch onto a port it cannot own.

### 2. Managed browser now defaults to Chrome for Testing

Normal system Chrome is no longer an implicit default candidate.

Resolution order:

1. explicit `MO2_AUTOMATION_BROWSER` / `MO2_CHROME_FOR_TESTING`;
2. already-installed project-managed Chrome for Testing;
3. automatically install current stable Chrome for Testing;
4. system Chrome only when explicitly allowed with `--allow-system-chrome` or `MO2_ALLOW_SYSTEM_CHROME=1`.

This keeps the remote-debugging browser isolated from the user's daily browser and avoids machine-specific Chrome policy/process reuse problems.

### 3. Automatic safe CDP port fallback

If the normal/persisted CDP port is occupied and `MO2_CDP_PORT` was not explicitly forced, the manager searches a nearby free localhost port and stores it in:

```text
.runtime/state/browser-port.json
```

Every later project process reads that persisted port.

If the user explicitly sets `MO2_CDP_PORT`, the manager will not silently override it.

## Full-update behavior

`npm run update` still starts the managed browser *before* the expensive full-library scan.

Therefore:

- managed browser healthy -> proceed to Update Eligibility / Component Discovery / downloads;
- managed browser cannot be established -> fail fast before the 1999-mod scan;
- ordinary per-item failures later in download mode still use `--continue-on-error`.

A browser failure must never again produce a long scan whose confirmed download targets all become `HOLD_COMPONENT_DISCOVERY` solely because browser coverage was unavailable.
