# v3.6 Patch Discovery Graph

## Problem

A correct MAIN file is not enough. Skyrim compatibility patches are frequently located in:

- Optional/Misc files on the same Nexus page;
- independent Patch Hub pages;
- pages listed under **Mods requiring this file**;
- compatibility links in Description/Installation text;
- FOMOD options;
- already-installed local patch entries that also need updating.

Therefore the system must distinguish:

1. **discovery** — what patch candidates exist;
2. **applicability** — which candidates matter for this MO2 setup;
3. **identity** — which exact Nexus file is correct;
4. **execution** — downloading each required file only after MAIN is verified.

## Pipeline

```text
MO2 local source + Nexus files
        |
        v
Deterministic MAIN selection
        |
        v
Patch Discovery Graph
  | same-page Files
  | Mods requiring this file
  | Description compatibility links/text
  | learned independent patch relations
  | installed MO2 context
  | local FOMOD evidence
        |
        v
all coverage proven?
  no -> HOLD_PATCH_DISCOVERY
        |
        yes
        v
all candidate families resolved?
  no -> HOLD_PATCH_DISCOVERY
        |
        yes
        v
aux-registry / exact REQUIRED file audit
        |
        v
closure gate
        |
        v
MAIN -> VERIFIED -> PATCH(es) -> VERIFIED -> TRANSLATION -> VERIFIED
```

## Discovery artifacts

Every audit creates:

```text
.runtime/runs/<timestamp>/patch-discovery.json
.runtime/runs/<timestamp>/patch-discovery-tasks.tsv
```

`patch-discovery.json` contains source coverage, candidates, family classification, local-context matches, registry decisions and unresolved items.

`patch-discovery-tasks.tsv` is designed for Pi/AI Agents. It contains two task types:

- `COVERAGE:*` — a required discovery source was not proven complete;
- `UNRESOLVED_PATCH` — a concrete candidate family needs a decision.

## Patch family decisions

`config/aux-registry.tsv` v3 adds a `family` column.

```text
mainModId mainFileId mainVersion kind family status auxModId auxFileId auxVersion auxName checkedAt evidence note
```

For PATCH, valid resolved states are:

- `REQUIRED`
- `NOT_APPLICABLE`
- `ALREADY_INCLUDED`
- `OBSOLETE`

A discovered family cannot be silenced by a blanket `PATCH NONE`.

When discovery coverage is complete and zero candidates exist, the discovery report itself proves Patch closure; a redundant PATCH NONE row is not necessary.

## Independent pages

`config/patch-relations.tsv` is a learned relation cache:

```text
mainModId auxModId family source note
```

Adding a relationship does **not** authorize a download. It only makes future audits re-check that independent page/candidate. Exact REQUIRED files still need aux-registry v3 + Nexus API audit.

## Strictness

v3.6 deliberately prefers false negatives:

- Browser unavailable -> discovery coverage incomplete -> HOLD.
- Requirements section cannot be proven inspected -> HOLD.
- Candidate family exists without a registry decision -> HOLD.
- REQUIRED candidate lacks exact current fileId -> HOLD.
- Evidence is stale -> HOLD.

This is intentional. The objective is to prevent `MAIN downloaded, Patch forgotten` rather than maximize automatic download count.
