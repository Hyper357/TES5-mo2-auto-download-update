# v4.1.1 — One-click Full Update Workflow

## Goal

Eliminate the UX gap where Pi finishes AUDIT, reports `UPDATE_CONFIRMED`, and then asks the user whether it should continue downloading.

A complete update is one continuous workflow:

```text
Browser / Preflight
→ full-library scan
→ Update Eligibility
→ Main / Variant
→ Component Discovery / Closure
→ automatic safe downloads
→ per-item VERIFIED
→ Review Center for deferred items
```

## User-facing entrypoints

### Full update

```powershell
npm run update
```

This command is itself explicit authorization for real downloads that pass every existing safety gate. It automatically:

- starts/validates the project-managed browser;
- runs a fresh scan;
- enables `--go`;
- enables `--continue-on-error` so one ordinary item failure does not stop later safe transactions;
- keeps debug evidence;
- leaves ambiguous/unsafe items as HOLD;
- opens Review Center after the automatic stage when review items exist.

It does **not** authorize installation, FOMOD clicking, enabling/disabling mods, priority changes, or plugin sorting.

### Audit only

```powershell
npm run audit
```

Use only when the user explicitly wants to inspect the library without real downloads.

## Natural-language intent for Pi

Treat these as FULL UPDATE:

```text
开始项目
开始更新
跑完整流程
更新我的 MOD
开始完整更新
```

Treat these as AUDIT ONLY:

```text
检查一下
扫描一下
看看有哪些更新
只审计
不要下载
```

In FULL UPDATE, Pi must not stop again after:

- `updates:status`;
- the count of `UPDATE_CONFIRMED` items;
- Main/Variant planning;
- Component discovery;
- splitting automatic vs human-review items.

Those are internal stages, not new authorization boundaries.

## Failure semantics

`npm run update` uses continue-on-item-error behavior. A failed NXM/CDN/MO2 transaction remains NOT VERIFIED and is reported, while later safe transactions continue.

The entire workflow may still stop for hard safety failures such as an untrusted browser session, failed Preflight, missing essential configuration, or a coordinator-level program failure.

VERIFIED items must never be blindly re-run to compensate for one failed item.
